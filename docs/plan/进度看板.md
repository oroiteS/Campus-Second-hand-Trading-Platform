## 📋 文档定位与维护规则

本看板是全部开发任务的**调度与状态唯一事实源**：批次进度、任务行、槽位占用、审查轮次、联调结果、收尾核验均以此为准。任何 agent 不得凭对话记忆调度。

1. **主 agent 唯一写入**；开发 / 审查 / 修复 / 联调 agent 与用户只读。
2. **更新时机与任务生命周期同步**：派发时登记任务行 → 每轮审查后追加留痕 → 用户确认后更新状态 → 并入集成分支 / 合入 main 时登记 → 收尾核验逐项打勾。
3. **留痕只追加不删改**：审查与联调记录即使后续被推翻也保留原行，新结论另起一行（保证"审查清零 / 联调通过"凭据链完整）。
4. 任务行 b1 起随该批任务计划定稿逐批补入；本骨架版先固定批次框架、槽位表与状态机。契约修订任务（`feat/api/*`）同样登记任务行，代号 `b<批次>api`，无隔离参数。

## 🔄 任务状态机（任务行「状态」列合法值）

```mermaid
stateDiagram-v2
    accTitle: 任务状态流转
    accDescr: 任务从待派发经开发、审查循环与用户确认后并入集成分支，联调发现单端缺陷可回退开发态修复重审，批次联调通过并合入主线后收尾归档。

    state "⏸ 待派发" as wait
    state "🔨 开发中" as dev
    state "🔍 审查中（第 N 轮）" as review
    state "🛠 修复中" as fix
    state "👤 待用户确认" as confirm
    state "✅ 已并入集成分支" as merged
    state "📦 已收尾" as done

    wait --> dev: 派发任务卡、建 worktree
    dev --> review: 开发自检全绿交付
    review --> fix: 本轮有阻断问题
    fix --> review: 修复后复审
    review --> confirm: 某轮零阻断且已汇报
    confirm --> merged: 用户通过 → 并入 + 清理开发 worktree
    confirm --> fix: 用户要求调整
    merged --> dev: 联调发现单端缺陷（回开发分支修复重审再并入）
    merged --> done: 批次联调通过 + 合入 main + 集成清理
```

状态标注格式：`🔍 审查中（第 2 轮 · 1 阻断）`——括号内为最新一轮摘要，明细见留痕。
